# 02 · 架构与模块导航

> 面向谁：要动代码的人。读完能得到什么：知道 10 个容器对应哪些代码、跨服务怎么调、一笔订单的数据怎么流。

## 1. 服务拓扑（已落地）

```
                      ┌──────────────────────────────┐
   浏览器 / 小程序 ──▶ │ duoduo-gateway :8080（唯一入口）│
                      │  路由 + JWT 校验 + 身份透传 + CORS │
                      └─┬────────┬────────┬────────┬────┬───┘
                        │        │        │        │    │
          lb://duoduo-user  lb://product  lb://trade  lb://fulfilment  lb://marketing  lb://ai
                 8081          8082        8083          8084           8085        8086
                        └────────┴────┬───┴────────┴────┴─────────────┴───────────┘
                               Nacos :8848（服务发现）
                    MySQL :3306（五库）   Redis :6379   Elasticsearch :9200（可选，profile=search）

  旁路（不进网关白名单的组合）：product ──(Feign, X-Internal-Token)──▶ ai 的候选召回 ← 只有 product 被 ai 调，
  而 ai 本身**不连库**（无状态）；ES 只被 product 读写，且**只做加速**，库始终是权威数据源。
```

**分层纪律（项目约定，评审会查）**：
- Controller 只做「参数绑定 + 调服务 + 包响应」，**不写业务逻辑**；
- Service 不依赖 `HttpServletRequest`，业务规则集中在 Service；
- 数据访问统一走 Mapper（MyBatis-Plus），参数化查询，**禁止字符串拼接 SQL**；
- 服务间调用**不经网关**（网关是对外入口）：用 Feign + `lb://` + `X-Internal-Token`。

## 2. 模块 ↔ 目录 ↔ 职责

| 模块 | 目录 | 职责 | 备注 |
|---|---|---|---|
| `duoduo-common` | `duoduo-common/` | 统一响应 `ApiResponse` / `PageResult`、`ErrorCode`、`BizException`、雪花 ID、`UserContext`/`LoginUser`、JWT 工具、`OperatorGuard` | 被所有服务依赖 |

| `duoduo-user` | `duoduo-user/` | 注册/登录/刷新令牌、实名、申请卖家、宠物档案、**内部批量昵称头像** | 库 `duoduo_user` |
| `duoduo-product` | `duoduo-product/` | 类目/品牌/SPU-SKU 检索、C2C 闲置、**库存主数据**、商家商品管理、后台类目品牌与内容审核 | 库 `duoduo_product` |
| `duoduo-trade` | `duoduo-trade/` | 购物车、下单拆单、库存冻结台账、订单状态机、支付渠道、资金托管与放款、卖家中心、后台订单干预与对账 | 库 `duoduo_trade` |
| `duoduo-fulfilment` | `duoduo-fulfilment/` | 评价与晒单 / 售后仲裁（A3）/ 物流轨迹（A2）/ 信用分（A4） | 库 `duoduo_fulfilment`；worker-id=4 |
| `duoduo-marketing` | `duoduo-marketing/` | **优惠券（A5）**：领券中心 / 我的券包 / 结算可用券 / 运营建券 / 内部锁·解·核销·补偿调度 | 库 `duoduo_marketing`；worker-id=5；端口 8085 |
| `duoduo-ai` | `duoduo-ai/` | **AI 导购「多多」（A9）**：`/api/duoduo/chat` 与 `/api/duoduo/capabilities`；经 Feign 调商品域候选召回，再交给 DashScope（或 mock）组织回复 | **无状态**：不连库、v1 不落对话历史；端口 8086；未配 `DASHSCOPE_API_KEY` 时走 mock 或降级 503 |
| `duoduo-common-web` | `duoduo-common-web/` | 公共 Servlet 侧件：全局异常、请求 ID、身份拦截、**`LongToStringJacksonModule`（A8 · 全局 ID 序列化，改 DTO 前必读）** | 改动影响**所有服务出参**，属高风险；改后必须 `mvn clean install`（见 08 篇 T-41）；**新增金额/计数类 `long` 字段要同时补进 `NUMERIC_LONG_FIELDS` 白名单**（漏列会让它被当标识转成字符串，见 T-56） |
| `frontend` | `frontend/` | React 18 + TS strict + Vite 5；买家端 / 商家端 / 平台后台 / 评价 / **优惠券** / **地址簿** / **AI 导购**七大页面域 | 见 06 篇 |

雪花 ID worker-id 分配（**新增服务必须挑一个没用过的**）：用户 1 / 商品 2 / 交易 3 / 履约 4 / **营销 5**。

## 3. 跨域调用清单（谁调谁、为什么）

| 调用方 → 被调方 | 接口 | 保护方式 | 字段裁剪 |
|---|---|---|---|
| trade → product | `/api/products/internal/skus/batch`、`/api/products/skus/stock/{freeze,release,deduct,restock}` | `X-Internal-Token` | 库存写接口只收数量与幂等键 |
| trade → trade（内部） | `/api/orders/internal/{orderNo}/{refund}`、`/internal/sweep` | `X-Internal-Token`（`InternalTokenFilter`） | — |
| **fulfilment → trade** | `GET /api/orders/internal/{orderNo}/fact` | `X-Internal-Token` | **不含收货人姓名/电话/地址** |
| **fulfilment → user** | `GET /api/users/internal/briefs?ids=` | `X-Internal-Token` | **只回 id/昵称/头像三字段** |
| **trade → marketing** | `POST /api/coupons/internal/{lock,release,consume,sweep}` | `X-Internal-Token` | 只传 `code` / `userId` / `orderNo` / `orderAmount`（**营销域不反查订单**；折扣金额由交易域写入 `t_order.discount_amount`） |

> 两条设计原则（评审时被反复引用）：
> ① **内部接口按「调用方真正需要什么」裁剪字段** —— 顺手返回整份视图，等于把隐私数据多复制进一个不需要它的服务；
> ② **批量而非逐条** —— 列表页 N 条数据逐条调对端就是 N 次跨进程往返（跨服务版 N+1）。

## 4. 一笔订单的数据流（主线）

```
加购      POST /api/cart/items            → trade 调 product 取 SKU 快照（价格/可售）
下单      POST /api/orders                → 幂等键 + 唯一索引防重；调 product **冻结库存**；落订单与明细快照
                                          → 若带券：调 marketing **锁券**（失败抛 422 带人话原因，如「满 200 元可用」）
支付      POST /api/orders/{no}/pay       → 渠道预下单（沙箱返回二维码内容 + 过期时间）
回调/扫码 POST /api/payments/callback|sandbox/{payNo} → 验签 + 金额核对 + CAS 幂等入账
                                          → 订单 PAID；**资金进平台托管**（t_settlement）；调 marketing **核销券**（失败则整笔支付不成立）
发货      POST /api/seller/orders/{no}/ship（或内部凭据） → SHIPPED；资金仍托管
收货      POST /api/orders/{no}/confirm   → COMPLETED；**放款给卖家**（扣平台佣金）；冻结库存转实扣
评价      POST /api/reviews               → fulfilment 读订单事实校验（本人 + 已完成）后落评价
退款      POST /api/seller/orders/{no}/refund → REFUNDED（钱退回买家）+ 退货入库补偿；**券不退回**（v1，退款退实付）
取消/关单  POST /api/orders/{no}/cancel（或强关 / 超时关单） → 调 marketing **解锁券**（锁定 TTL 兜底由 sweep 扫）
```

**关键工程取舍**（细节见 README §四/§五）：
- 幂等一律靠**唯一索引**（`uk_order_user_idem`、`uk_pay_channel_idem`、`uk_review_order_user_spu`、**`uk_coupon_user_tpl`**），不靠分布式锁；
- 库存扣减用**原子条件更新**（判断写进 WHERE），可售 = `stock - frozen_stock`；
- 超时关单 / 自动确认收货由 `@Scheduled` 扫描，**幂等可重入**，手动 `/internal/sweep` 便于排障与测试；
- 金额一律**整数分**，时间一律 **UTC**。

## 5. 与 `docs/ARCHITECTURE.md` 的关系

`ARCHITECTURE.md` 是**长期设计蓝图**（12 服务拆分、分库分表、容量模型、降级矩阵），
