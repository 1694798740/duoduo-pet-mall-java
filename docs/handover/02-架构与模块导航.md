# 02 · 架构与模块导航

> 面向谁：要动代码的人。读完能得到什么：知道 8 个容器对应哪些代码、跨服务怎么调、一笔订单的数据怎么流。

## 1. 服务拓扑（已落地）

```
                      ┌──────────────────────────────┐
   浏览器 / 小程序 ──▶ │ duoduo-gateway :8080（唯一入口）│
                      │  路由 + JWT 校验 + 身份透传 + CORS │
                      └───────┬──────────┬───────────┬───┘
                              │          │           │
                   lb://duoduo-user  lb://product  lb://trade  lb://fulfilment
                          8081          8082         8083         8084
                              └──────────┴─────┬─────┴────────────┘
                                     Nacos :8848（服务发现）
                              MySQL :3306（四库）   Redis :6379
```

**分层纪律（项目约定，评审会查）**：
- Controller 只做「参数绑定 + 调服务 + 包响应」，**不写业务逻辑**；
- Service 不依赖 `HttpServletRequest`，业务规则集中在 Service；
- 数据访问统一走 Mapper（MyBatis-Plus），参数化查询，**禁止字符串拼接 SQL**；
- 服务间调用**不经网关**（网关是对外入口）：用 Feign + `lb://` + `X-Internal-Token`。

## 2. 模块 ↔ 目录 ↔ 职责

| 模块 | 目录 | 职责 | 备注 |
|---|---|---|---|
| `duoduo-common` | `duoduo-common/` | 统一响应 `ApiResponse` / `PageResult`、`ErrorCode`、`BizException`、雪花 ID、`UserContext`/`LoginUser`、JWT 工具、`OperatorGuard` | 被所有服务依赖 |
| `duoduo-common-web` | `duoduo-common-web/` | Servlet 侧基础设施：全局异常处理、请求 ID、身份上下文透传（`X-User-*`） | 仅 Web 服务依赖 |
| `duoduo-gateway` | `duoduo-gateway/` | Spring Cloud Gateway（WebFlux）：路由、JWT 前置校验、白名单、身份头注入、CORS | 白名单在 `GatewaySecurityProperties` |
| `duoduo-user` | `duoduo-user/` | 注册/登录/刷新令牌、实名、申请卖家、宠物档案、**内部批量昵称头像** | 库 `duoduo_user` |
| `duoduo-product` | `duoduo-product/` | 类目/品牌/SPU-SKU 检索、C2C 闲置、**库存主数据**、商家商品管理、后台类目品牌与内容审核 | 库 `duoduo_product` |
| `duoduo-trade` | `duoduo-trade/` | 购物车、下单拆单、库存冻结台账、订单状态机、支付渠道、资金托管与放款、卖家中心、后台订单干预与对账 | 库 `duoduo_trade` |
| `duoduo-fulfilment` | `duoduo-fulfilment/` | **评价与晒单**（后续：物流轨迹 / 售后仲裁 / 信用分） | 库 `duoduo_fulfilment`；worker-id=4 |
| `frontend` | `frontend/` | React 18 + TS strict + Vite 5；买家端 / 商家端 / 平台后台 / 评价四大页面域 | 见 06 篇 |

雪花 ID worker-id 分配（**新增服务必须挑一个没用过的**）：用户 1 / 商品 2 / 交易 3 / 履约 4。

## 3. 跨域调用清单（谁调谁、为什么）

| 调用方 → 被调方 | 接口 | 保护方式 | 字段裁剪 |
|---|---|---|---|
| trade → product | `/api/products/internal/skus/batch`、`/api/products/skus/stock/{freeze,release,deduct,restock}` | `X-Internal-Token` | 库存写接口只收数量与幂等键 |
| trade → trade（内部） | `/api/orders/internal/{orderNo}/{refund}`、`/internal/sweep` | `X-Internal-Token`（`InternalTokenFilter`） | — |
| **fulfilment → trade** | `GET /api/orders/internal/{orderNo}/fact` | `X-Internal-Token` | **不含收货人姓名/电话/地址** |
| **fulfilment → user** | `GET /api/users/internal/briefs?ids=` | `X-Internal-Token` | **只回 id/昵称/头像三字段** |

> 两条设计原则（评审时被反复引用）：
> ① **内部接口按「调用方真正需要什么」裁剪字段** —— 顺手返回整份视图，等于把隐私数据多复制进一个不需要它的服务；
> ② **批量而非逐条** —— 列表页 N 条数据逐条调对端就是 N 次跨进程往返（跨服务版 N+1）。

## 4. 一笔订单的数据流（主线）

```
加购      POST /api/cart/items            → trade 调 product 取 SKU 快照（价格/可售）
下单      POST /api/orders                → 幂等键 + 唯一索引防重；调 product **冻结库存**；落订单与明细快照
支付      POST /api/orders/{no}/pay       → 渠道预下单（沙箱返回二维码内容 + 过期时间）
回调/扫码 POST /api/payments/callback|sandbox/{payNo} → 验签 + 金额核对 + CAS 幂等入账
                                          → 订单 PAID；**资金进平台托管**（t_settlement）
发货      POST /api/seller/orders/{no}/ship（或内部凭据） → SHIPPED；资金仍托管
收货      POST /api/orders/{no}/confirm   → COMPLETED；**放款给卖家**（扣平台佣金）；冻结库存转实扣
评价      POST /api/reviews               → fulfilment 读订单事实校验（本人 + 已完成）后落评价
退款      POST /api/seller/orders/{no}/refund → REFUNDED（钱退回买家）+ 退货入库补偿
```

**关键工程取舍**（细节见 README §四/§五）：
- 幂等一律靠**唯一索引**（`uk_order_user_idem`、`uk_pay_channel_idem`、`uk_review_order_user_spu`），不靠分布式锁；
- 库存扣减用**原子条件更新**（判断写进 WHERE），可售 = `stock - frozen_stock`；
- 超时关单 / 自动确认收货由 `@Scheduled` 扫描，**幂等可重入**，手动 `/internal/sweep` 便于排障与测试；
- 金额一律**整数分**，时间一律 **UTC**。

## 5. 与 `docs/ARCHITECTURE.md` 的关系

`ARCHITECTURE.md` 是**长期设计蓝图**（12 服务拆分、分库分表、容量模型、降级矩阵），
其中不少服务（履约完整版 / 营销 / AI / 检索）尚未实现；**已落地现状以 README §二/§三 与本篇为准**。
规划与现状的差距清单见 `08-风险、已知边界与接手建议.md`。
