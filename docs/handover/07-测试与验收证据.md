> 面向谁：提交前要自测的人、要加新测试的人、要判断「这版能不能上」的人。
> 一句话：本项目**没有单元测试框架，全部验收靠端到端冒烟 + 真实浏览器自测**，这是刻意的选择（见 §4）。

## 3. 脚本的四条共同约定（踩过坑才有的）

1. **每次运行使用随机手机号**，脚本可重复执行，不污染种子数据；
2. **夹具（价格/库存/佣金）一律从接口动态取**，不硬编码 —— 否则种子数据一改，测试就会「通过但其实是错的」；
3. **凡改库必先记录原值、结尾复原并自证**（部分脚本支持 `-SkipDbCheck` 只跑接口断言）；
4. **跨轮次断言按「本次测试开始时间」限定范围**，不被历史数据误伤。

## 4. 为什么不做单元测试（以及什么时候该补）

- 本项目选择**端到端冒烟**为主：微服务的主要风险在**跨服务契约、状态机、幂等与并发**，
  这些用 mock 掉的单测基本测不出来（例如「订单已取消、二维码还能扫出钱」这类缺陷只有真链路才现形）。
- 代价：跑一轮全绿约需数分钟、且依赖容器环境。**如果接手后要长期演进，建议补两类单测**：
  ① 金额/佣金/退款金额计算（纯函数，最容易算错且后果最贵）；
  ② 状态机迁移合法性（枚举 + 迁移矩阵，改动频繁）。

## 5. 历史自测暴露的真实缺陷（说明这套测试是有效的）

| 轮次 | 缺陷 | 后果 |
|---|---|---|
| M5 | 幽灵冻结：部分成功时已冻成功的 SKU 被漏记补偿 | 库存永久冻住 |
| M5 | 已付款可自助取消 / 超时关单不释放冻结 / 并发释放被记成失败 | 资金与库存双错 |
| M8 | 未知渠道与 MOCK 回调拒绝用了 400；二维码指向直连地址扫码不可达；**订单取消不作废支付单** | 订单已取消还能付钱 |
| M9 | 客户端发错 Content-Type 落到兜底返回 **500**；物流单号只写日志没落订单 | 客户端错误污染 5xx 告警；卖家看不到自己填的单号 |
| M10 | product 服务 `id-type: input` 未显式赋主键 → 创建类目 500；审核动词与状态常量比较错位 → 全部审核 422；**后台列表复用只含 ACTIVE 的查询 → 停用即消失无法恢复** | 运营流程断裂 |
| M11 | 内部接口断言打错服务端口；PowerShell `$VAR?` 吞查询串；20 位雪花 ID 丢精度致假失败；「商品不在订单中」400 应归 422 | 排障误导 |
| 第十三轮 A5（实现） | ① **未登录访客被标成「可领取」**：`toTemplateView` 没把登录态传进去，前端渲染一个注定 401 的「立即领取」按钮 → 加 `loggedIn` 分支（`claimable=false` + 文案「登录后可领取」）；② **`cancel` 路径漏了解锁券**：只有强关与超时关单会解锁，用户主动取消时券卡在 `LOCKED` 直到 TTL → `cancel` 补 `releaseCouponQuietly(orderNo,"用户取消")`，三处统一带 `scene`；③ `OrderService` 构造器漏赋值 `marketingGateway`（编译期即拦截） | 用户看到「立即领取」却 401；券被无效占用 |
| 第十三轮 A5（工程） | `coupon-smoke.ps1` **首跑 143 通过 / 2 失败**，失败项恰是新加的两条「未登录应不可领 / 文案为『登录后可领取』」，**而源码里该分支明明存在** —— 根因不是代码，是**容器**：`loggedIn` 修复写进源码后没重建 `duoduo-app-marketing`，跑的是旧镜像。修法 `docker compose build duoduo-marketing-app && docker compose up -d duoduo-marketing-app` 后 **145/145 全绿**（见 `08` 篇 **T-37**） | 「代码对、断言错、curl 也看不到新分支」的典型误判 |
| 第十三轮 A5（环境） | 本机 **Node 无法创建子进程**（`spawnSync`/`execFileSync` 一律 `EBUSY errno -4082`），e2e 夹具不能在 Node 里跑 SQL → 改为 PowerShell 建/删夹具（见 `08` 篇 **T-38**） | 环境限制，非代码问题 |
| 第十四轮 A8（实现） | ① **T-39 雪花 ID 精度丢失**：18~19 位 ID 以 JSON number 下发，浏览器 `JSON.parse` **静默四舍五入**（`...704`→`...700`，不报错）→ 前端拼 URL 404。**冒烟脚本照不出来**（PowerShell/.NET 用 Int64 解 JSON 不丢精度），**只有真实浏览器会踩**。A3 曾局部规避一次（`String.valueOf(AfterSaleView.id)`），A8 又踩一次 → 本轮改为**全局根治**（`LongToStringJacksonModule`）；② **T-42 结算页竞态**：`useAsync` 初始 `data` 是 `undefined` 而非 `null`，`Checkout.tsx` 守卫写成 `addressList === null` 是**死代码** → 有地址的用户被推进手动填写模式 | 前端 404 / 用户被迫手填（正是「脚本全绿、浏览器全红」的典型） |
| 第十四轮 A8（工程） | **T-41 增量打包陷阱**：改公共模块后 `mvn package` 是**增量**的，业务模块源码没动 → **业务 fat jar 不重打**（只重打 common-web），Dockerfile `COPY` 的仍是内嵌旧 common-web 的旧 jar → 现象是「代码对、容器里跑的不是这份代码」。判据是**包 jar 的 mtime**；「构建几秒就 EXIT=0」是危险信号。修法 `mvn -DskipTests clean install` → `docker compose build --no-cache` → `up -d --force-recreate`。另：`docker compose up -d <svc>` 在镜像 id 变了但容器配置没变时**不会换容器** | 白名单「不生效」的假象（`price` 仍是 `"12900"`） |
| 第十四轮 A8（脚本自身） | 批量回归首次跑出 3 套红：① `run-all-smoke.ps1` **自我递归**（文件名匹配 `*-smoke.ps1`）→ 排除自身；② `review-smoke.ps1` 抠主键正则 `'"id":(\d+)'` 匹配不到新形态（ID 已是字符串）→ 改 `'"id"\s*:\s*"?(\d+)"?'`；③ `order-smoke.ps1` 的「缺收货人被拦截」用例**撞上「购物车为空」的 422**（同码不同因）→ 补「先加购」前置 + 同时断言 `code == 'VALIDATION_ERROR'` | 假绿灯 / 自我递归（**断言只查状态码不够**的铁证） |

## 6. 提交流程（与本包其它篇一致）

1. 改代码 → 单模块打包（**带 `-am`**）→ `docker compose build/up` 重建对应容器；
2. 跑**受影响的冒烟脚本**（至少一套，涉及跨域调用时跑上下游两套）；
3. 前端改动跑 `tsc --noEmit` + `vite build`，UI 改动再跑对应 `*-ui-check.mjs`；
4. 更新 `docs/PLAN.md`（进度/变更记录/命令速查）+ 云端台账 + 事项表；
5. 提交推送 GitHub **并在同一次提交里更新 README.md**。
