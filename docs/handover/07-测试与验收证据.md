## 3. 脚本的四条共同约定（踩过坑才有的）

1. **每次运行使用随机手机号**，脚本可重复执行，不污染种子数据；
2. **夹具（价格/库存/佣金）一律从接口动态取**，不硬编码 —— 否则种子数据一改，测试就会「通过但其实是错的」；
3. **凡改库必先记录原值、结尾复原并自证**（部分脚本支持 `-SkipDbCheck` 只跑接口断言）；
4. **跨轮次断言按「本次测试开始时间」限定范围**，不被历史数据误伤。

## 4. 为什么不做单元测试（以及什么时候该补）

- 本项目选择**端到端冒烟**为主：微服务的主要风险在**跨服务契约、状态机、幂等与并发**，
  这些用 mock 掉的单测基本测不出来（例如「订单已取消、二维码还能扫出钱」这类缺陷只有真链路才现形）。
- 代价：跑一轮全绿约需数分钟、且依赖容器环境。**如果接手后要长期演进，建议补两类单测**：
  ① 金额/佣金/退款金额计算（纯函数，最容易算错且后果最贵）；
  ② 状态机迁移合法性（枚举 + 迁移矩阵，改动频繁）。

## 5. 历史自测暴露的真实缺陷（说明这套测试是有效的）

| 轮次 | 缺陷 | 后果 |
|---|---|---|
| M5 | 幽灵冻结：部分成功时已冻成功的 SKU 被漏记补偿 | 库存永久冻住 |
| M5 | 已付款可自助取消 / 超时关单不释放冻结 / 并发释放被记成失败 | 资金与库存双错 |
| M8 | 未知渠道与 MOCK 回调拒绝用了 400；二维码指向直连地址扫码不可达；**订单取消不作废支付单** | 订单已取消还能付钱 |
| M9 | 客户端发错 Content-Type 落到兜底返回 **500**；物流单号只写日志没落订单 | 客户端错误污染 5xx 告警；卖家看不到自己填的单号 |
| M10 | product 服务 `id-type: input` 未显式赋主键 → 创建类目 500；审核动词与状态常量比较错位 → 全部审核 422；**后台列表复用只含 ACTIVE 的查询 → 停用即消失无法恢复** | 运营流程断裂 |
| M11 | 内部接口断言打错服务端口；PowerShell `$VAR?` 吞查询串；20 位雪花 ID 丢精度致假失败；「商品不在订单中」400 应归 422 | 排障误导 |

## 6. 提交流程（与本包其它篇一致）

1. 改代码 → 单模块打包（**带 `-am`**）→ `docker compose build/up` 重建对应容器；
2. 跑**受影响的冒烟脚本**（至少一套，涉及跨域调用时跑上下游两套）；
3. 前端改动跑 `tsc --noEmit` + `vite build`，UI 改动再跑对应 `*-ui-check.mjs`；
4. 更新 `docs/PLAN.md`（进度/变更记录/命令速查）+ 云端台账 + 事项表；
5. 提交推送 GitHub **并在同一次提交里更新 README.md**。
