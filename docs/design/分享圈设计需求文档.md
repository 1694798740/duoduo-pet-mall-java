# 分享圈设计需求文档（商品分享 + 评论 · 跳蚤市场 C2C）

> 版本：v1.0（第四十八轮）｜状态：评审稿
> 范围：分享圈「商品分享 + 评论体系」与「跳蚤市场（C2C 二手交易）」两个方向的完整设计需求
> 读者：产品 / 前后端 / 测试。所有设计均已对照现有代码库（服务、表、页面），
> 标注「已有」「新增」「改造」，杜绝凭空设计。

---

## 1. 背景与目标

分享圈（第四十三~四十七轮）已上线商品分享、点赞、收藏、转发、关注与私信；
「问一问」打通了商品页 → 卖家/客服的咨询链路。下一阶段要把分享圈从
「内容浏览社区」升级为「内容 + 交易闭环社区」，对标闲鱼的产品形态：

| 目标 | 度量 |
|---|---|
| 分享内容可被讨论，沉淀社区氛围 | 分享的评论率（评论数/浏览数） |
| 用户能把手里的宠物用品挂出来卖掉 | 挂单数、挂单成交转化率 |
| C2C 交易资金安全可控 | 托管-放款/退款全走 t_settlement CAS，0 线下转账纠纷 |

**不做**的事也先说清楚（边界见 §9）。

---

## 2. 用户角色与核心场景

| 角色 | 描述 | 核心场景 |
|---|---|---|
| 浏览者 | 未登录或登录但不发布 | 逛圈子、看商品分享/闲置、评论互动 |
| 分享者 | 登录用户 | 分享商城商品到圈子并参与讨论 |
| 闲置卖家 | 登录用户（个人） | 发布闲置（需审核）、回复咨询、发货、收款 |
| 闲置买家 | 登录用户 | 逛集市、私聊砍价、下单担保支付、确认收货 |
| 平台 | 管理端 | 闲置审核、评论治理、纠纷仲裁（退款） |

核心用户旅程（对标闲鱼「刷→问→拍→收」）：

```
逛分享圈/集市 → 看中闲置 → 私聊卖家（复用问一问链路）→ 下单（担保托管）
→ 卖家发货（复用物流域）→ 买家确认收货 → 托管放款给卖家 → 互评
```

### 3.1 服务与页面

| 资产 | 现状 | 复用方式 |

| 分享圈 feed / 详情页 | `pages/share-circle`、`pages/share-detail`；分享/点赞/收藏/转发已上线 | 评论挂进详情页；feed 增加闲置卡类型 |

## 4. 功能需求 A：商品分享 + 评论体系

### 4.1 评论模型

- **两级结构**（对标主流社区，闲鱼同款）：
  - 一级评论：直接对分享发表；
  - 二级回复：挂在某条一级评论下，`@某人` 语义；
  - 不做三级及以上（无限楼中楼会失控，两级 + 回复人字段足够表达）。
- 计数冗余：`t_product_share` 增加 `comment_count` 冗余列（与 like_count 同款纪律），
  列表页不做 COUNT 聚合。

### 4.2 功能点

| 编号 | 需求 | 优先级 |
|---|---|---|
| A-1 | 分享详情页展示评论列表（时间正序，分页 20 条） | P0 |
| A-2 | 登录用户可发一级评论（1~500 字，内容 strip 后非空） | P0 |
| A-3 | 登录用户可回复一级评论（二级），回复数显示在一级评论下 | P0 |
| A-4 | 删除自己的评论（软删，`deleted=1`，楼中楼保留「该评论已删除」占位） | P1 |
| A-5 | 评论点赞（对评论本身），P1 先做计数不做列表 | P1 |
| A-6 | 发评论/被评论触发社交通知（复用 `t_social_notice`：COMMENT / REPLY 两类） | P1 |
| A-7 | 管理端评论治理：删除违规评论（软删 + 治理原因） | P1 |
| A-8 | 分享卡片显示最新 2 条评论摘要在详情页底部 | P2 |

### 4.3 交互细节

- 未登录点评论框 → `requireLogin` 引导登录（与分享/点赞同一纪律，不静默登录）；
- 自己的评论长按 → 删除确认；别人的评论 → 回复；
- 评论框固定在详情页底部，仿聊天输入条；
- 发布成功后列表**头部插入**新评论（本地 setData，不整页刷新）。

## 5. 功能需求 B：跳蚤市场（C2C，对标闲鱼）

### 5.1 挂闲置（发布）

| 编号 | 需求 | 优先级 |
|---|---|---|
| B-1 | 发布表单：标题(≤30字)/描述(≤500字)/价格(分)/成色/城市/图片(1~6张，复用产品图通道)/宠物种类的组合**与闲鱼对齐**：发布前必须完成实名或手机号实名校验，详见 §10 合规 | P0 |
| B-2 | 发布后 `audit_status=PENDING`，人工审核通过才对外（**已有机制**，直接沿用 AdminListingController） | P0 |
| B-3 | 我的闲置管理：上架/下架/编辑/删除（ON_SALE ↔ OFF_SHELF） | P0 |
| B-4 | 浏览量 `view_count`（已有列）详情页 +1 | P1 |

### 5.2 集市浏览

| 编号 | 需求 | 优先级 |
|---|---|---|
| B-5 | 集市页（新 tab 或分享圈子页内 segment）：卡片流（图/价/成色/城市/卖家昵称头像） | P0 |
| B-6 | 筛选：分类（复用商品类目）、成色、价格区间、城市；排序：最新/价格升降 | P1 |
| B-7 | 搜索：标题关键词（复用 ES 检索链路，索引扩 listing） | P1 |
| B-8 | 「关注卖家的闲置」子 tab | P2 |

### 5.3 交易闭环（核心）

| 编号 | 需求 | 优先级 |
|---|---|---|
| B-9 | 闲置详情页：图集/描述/成色/卖家卡（昵称+头像+信用分入口）/「我想要」按钮 | P0 |
| B-10 | 「我想要」→ 进入与卖家的私聊（**bizType=LISTING**，服务端以 listing.seller_id 定人，复用问一问的 ASK 定人纪律），会话豁免非互关限制，消息卡片带闲置缩略图 | P0 |
| B-11 | 私聊页内「拍下」入口 → 创建 C2C 订单（trade 域新入口，落 `t_order`，`order_type=C2C`，关联 listing_id） | P0 |
| B-12 | 支付走既有支付单（`t_payment`），成功后资金进托管（`t_settlement.status=CUSTODY`，已有 CAS 语义），同时 listing 锁定 `status=LOCKED` 防超卖 | P0 |
| B-13 | 卖家发货：复用 fulfilment 物流下单/轨迹（无第三方运单时支持「同城面交」标记，面交订单确认收货后直接放款） | P1 |
| B-14 | 买家确认收货 → `t_settlement` RELEASED 给卖家；申请退款 → 平台仲裁后 REFUNDED（已有 CAS 迁移，补管理端仲裁入口） | P0 |
| B-15 | 成交后 listing `status=SOLD`，集市不再展示；卖家可一键「重新上架」 | P0 |
| B-16 | 交易互评（买家评卖家、卖家评买家），进信用分体系（A4 轮已有信用分） | P2 |

### 5.4 与商城的边界

- 闲置不进购物车、不参与优惠券/秒杀（营销域不感知 C2C 订单）；
- C2C 订单不开发票、不进商城售后体系（走平台仲裁）；
- 集市商品与商城 SPU 完全隔离（两套卡片、两套详情页），避免混卖。

## 6. 数据模型设计

### 6.1 改造已有表

```sql
-- t_listing 增列（增量 SQL，幂等）
ALTER TABLE t_listing
  ADD COLUMN lock_order_id BIGINT NULL COMMENT '锁定该闲置的 C2C 订单号（LOCKED 时非空）',
  ADD COLUMN sold_at       TIMESTAMP NULL COMMENT '成交时间（SOLD 时非空）';

-- t_product_share 增列（评论计数冗余）
ALTER TABLE t_product_share
  ADD COLUMN comment_count INT NOT NULL DEFAULT 0 COMMENT '评论数（含回复，软删不计）';

-- t_social_message.biz_type 枚举扩 LISTING
-- （应用层 normalizeBizType 白名单 + DB 无枚举约束，只需代码放行）
```

### 6.2 新增表

```sql
-- 评论主表（两级：parent_id NULL=一级评论，否则为二级回复）
CREATE TABLE t_share_comment (
    id            BIGINT       NOT NULL,
    share_id      BIGINT       NOT NULL COMMENT '被评论的分享',
    user_id       BIGINT       NOT NULL COMMENT '评论人',
    parent_id     BIGINT       NULL COMMENT '一级评论 id（二级回复填）',
    reply_to_user BIGINT       NULL COMMENT '被 @ 的回复目标（二级才有）',
    content       VARCHAR(500) NOT NULL,
    like_count    INT          NOT NULL DEFAULT 0,
    deleted       TINYINT      NOT NULL DEFAULT 0 COMMENT '软删：1=用户删/2=治理删',
    created_at    TIMESTAMP    NOT NULL,
    PRIMARY KEY (id),
    KEY idx_comment_share (share_id, deleted, created_at),
    KEY idx_comment_parent (parent_id)
);

-- 评论点赞
CREATE TABLE t_share_comment_like (
    id         BIGINT   NOT NULL,
    comment_id BIGINT   NOT NULL,
    user_id    BIGINT   NOT NULL,
    created_at TIMESTAMP NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_comment_like (comment_id, user_id)
);
```

- C2C 订单复用 `t_order` + `order_type` 扩 `C2C`（含 `ref_listing_id` 扩列）；
- 交易互评 P2 阶段新建 `t_trade_review`，本稿不展开。

### 6.3 索引与量级预估

- 评论查询走 `(share_id, deleted, created_at)` 复合索引，一级评论分页 +
  每条的一级评论批量拉二级（`parent_id IN (...)`），避免 N+1；
- 集市列表走已有 `idx_listing_status`；价格/城市筛选在 P1 按需补
  `(audit_status, status, price)` 复合索引。

## 7. 接口设计草案（REST，沿用 ApiResponse 信封）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/socials/shares/{id}/comments?page&size` | 一级评论分页（带每条前 3 条回复摘要+回复总数） |
| POST | `/api/socials/shares/{id}/comments` | 发一级评论 `{content}` |
| POST | `/api/socials/shares/{id}/comments/{commentId}/replies` | 回复 `{content, replyToUserId?}` |
| DELETE | `/api/socials/comments/{id}` | 软删（本人或治理） |
| POST | `/api/socials/comments/{id}/like` | 评论点赞/取消（幂等翻转） |
| GET | `/api/listings?categoryId&condition&minPrice&maxPrice&city&sort&page` | 集市列表 |
| GET | `/api/listings/{id}` | 闲置详情（浏览量+1） |
| POST | `/api/listings` | 发布闲置（登录，落 PENDING） |
| PUT | `/api/listings/{id}/status` | 上架/下架（卖家本人） |
| POST | `/api/socials/messages` | bizType=LISTING（服务端按 listing 定人，复用 ASK 纪律） |
| POST | `/api/trades/c2c/orders` | C2C 下单 `{listingId}`，预占校验+托管创建 |
| POST | `/api/trades/c2c/orders/{id}/confirm` | 买家确认收货 → 放款（CAS） |

治理接口进 `AdminXxxController`：评论软删、闲置审核（已有）、C2C 退款仲裁。

## 10. 非功能与合规（审核红线）

| 项 | 要求 | 现状 |
|---|---|---|
| 资质与类目 | 二手/闲置交易涉及平台抽成或资金托管时，小程序类目与资质需支持「电商平台/二手」，**需核实微信最新类目要求** | 当前类目待核实 |
| 虚拟支付 | C2C 是实物交易走微信支付，不触 iOS 虚拟商品禁令；**但闲置发布若做「置顶付费」等虚拟服务，iOS 禁用** | 设计上规避 |
| 内容合规 | 闲置图片/文案过审核（人工审核已具备）；评论需敏感词过滤 + 治理入口 | 评论治理 P1 |
| 资金合规 | 全部资金走 t_settlement 托管 CAS，平台不经手线下转账；页面明示「担保交易，确认收货后打款」 | 复用既有 |
| 用户实名 | 发布闲置要求手机号实名即可下单交易；大额（≥2000 元）提示补充实名信息 | P1 |
| 隐私 | 不展示买卖双方手机号；私聊复用现有脱敏纪律 | 已具备 |

## 11. 明确不做（边界）

1. 无限层楼中楼、评论表情包自定义、弹幕——两级够用；
2. 闲鱼式「鱼小铺/主页装修」、直播卖货；
3. C2C 议价系统（改价邀约）——P1 先用私聊+卖家改价实现人肉议价；
4. 跨城物流比价、运费模板——C2C 统一包邮或面交，运费砍价不进系统；
5. 营销域（券/秒杀）与 C2C 的任何联动。

## 12. 风险与开放问题

| # | 风险/问题 | 处置 |
|---|---|---|
| 1 | listing 锁定与下单并发超卖 | `UPDATE ... SET status='LOCKED' WHERE id=? AND status='ON_SALE'` CAS，affected=0 即抢失败（与库存冻结同纪律） |
| 2 | 评论刷屏/广告 | 频控复用私信 429 纪律（每分钟 N 条）；治理软删 |
| 3 | 面交订单的放款依据 | 面交标记下买家点「已收到货」即放款，纠纷走仲裁；P1 评估强制确认延迟 |
| 4 | 闲置审核积压 | 管理端审核列表已具备；考虑 P2 自动化预审（图片涉黄接口） |
| 5 | 分享 feed 里闲置卡与商品卡的混排策略 | 推荐流默认只出商品分享，集市 segment 只出闲置（P0 简单清晰，P2 再谈混排） |
| 6 | 微信类目/资质结论未定 | **开放问题**：B-11（下单）上线前必须核实；在此之前 Batch-3 可先发测试版 |
```
