## 1. 全局约定

### 1.1 响应包络（所有接口）
```json
{ "code": "SUCCESS", "message": "ok", "data": <T | null>, "requestId": "hex", "timestamp": 1789700721253 }
```
分页：`data = { "items": [...], "total": n, "page": 1, "pageSize": 10, "pageCount": k }`（`page` 从 **1** 起）。
时间：**ISO-8601 UTC 字符串**（如 `"2026-09-18T03:51:24Z"`）。金额：整数**分**。

### 1.2 认证
| 头 | 由谁写入 | 说明 |
|---|---|---|
| `Cookie: access_token` / `refresh_token` | 服务端 Set-Cookie（httpOnly） | 前端**不**在 JS 里读令牌 |
| `X-User-Id` / `X-User-Phone` / `X-User-Role` | 网关校验令牌后注入 | 服务端从 `UserContext` 取；**客户端伪造的同名头会被网关剥离** |
| `X-Internal-Token` | 服务间调用（`InternalCallConfig`） | 校验方：user / product / trade / fulfilment / **marketing** 各自的 `InternalTokenFilter` |

| Java 类型 | 序列化结果 | 判据 |
|---|---|---|
| `Long` / `long` / `BigInteger`（**默认**） | **JSON 字符串**（如 `"361084524781768704"`） | 防止 18~19 位雪花 ID 被 JS `JSON.parse` 静默四舍五入 |
| `Long` 且**字段名命中白名单** | **JSON 数字** | 白名单按**字段语义**分三类：金额（单位分）/ 计数 / epoch 毫秒时间戳 |

白名单字段（`NUMERIC_LONG_FIELDS`，节选）：`price` / `payAmount` / `discountAmount` / `thresholdAmount` / `freight` / `balance` / `amount` / `quantity` / `availableStock` / `sales` / `count` / `size` / `timestamp` / `createTime` / `updateTime` / `expireAt` …

**三条硬纪律**：
1. **ID 类字段出前端一律用 `String`**（INV-16）——这是默认行为，不要「修回去」。
2. **不要把 `Long` 类型的金额/计数/时间戳加进「字符串化」清单**：全站金额字段共 **63 处都是 `Long`（分）**，若一刀切字符串化，JS 里 `"12900" / 100` → **`NaN`** → 页面金额全变「¥NaN」（T-40 的反例）。**判据是字段语义，不是 Java 类型**。
3. **反序列化不受影响**：入参仍可接受 number 或 string，前端不必改写请求体。

**第四十六轮 · 转发四字段语义**：`shareType` ∈ `ORIGINAL|REPOST`；`parentId/parentNickname/parentContent`
是被转原帖的 ID、作者昵称、评价内容（原创为 null）。**`userId / nickname / avatar` 恒是「本条分享的作者」**
—— 转发时即转发人本人，这是修复「详情页仍显示原发帖人」的关键：详情页按 `userId` 渲染，转发单天然以转发人为作者。

**业务规则（实现约束，改前先读 `ShareService`）**：
- **快照以商品域事实为准**：发布时经 Feign `ProductClient` 调商品域 `/api/products/internal/cards` 落
  `product_title/product_image/min_price` 快照；请求体没有标题/图片字段（公开信息流不可贴伪造商品卡）；
  商品不存在 → 404；商品域不可用 → 422 拒绝发布（写操作不静默降级成空白卡）。
- **公开读 / 登录写**：feed 与 detail 免登（与商品评价同一公开读口径）；网关白名单只放
  `/api/shares/feed` 与 `/api/shares/*` 两条只读路径——feed 刻意用两段路径与发布路径（单段）分开，
  白名单按路径匹配不区分方法，绝不能放 `/api/shares` 或 `/api/shares/**`。
  `AntPathMatcher` 的 `*` 不跨 `/`，所以 `/{id}/like`、`/{id}/favorite`、`/{id}/repost` 三类**两段**写路径
  都不在白名单内，一律强制登录（第四十四/四十六轮各验一次）。
- 昵称/头像复用 `loadBriefs` 批量补全，用户服务不可用降级「用户 {id}」；表 `t_product_share`
  （增量 `docs/sql/incremental/12-share-circle.sql`）。
- **互动（第四十四轮）**：`t_share_like` / `t_share_favorite` 两张同构表，`(share_id, user_id)`
  复合主键即唯一约束（一人一票，并发撞键幂等）；计数冗余在 `t_product_share.like_count /
  favorite_count`（信息流高频读不逐行 COUNT，回退 `GREATEST(0, n-1)` 防负漂移）；
  增量 `docs/sql/incremental/13-share-engagement.sql`。`likeCount/favoriteCount/count`
  已列入 `LongToStringJacksonModule` 数值白名单（计数必须为 JSON 数字）。
- **转发（第四十六轮）**：转发 = **又一次分享**，不是「引用展示」——插一条新 `t_product_share` 行
  （`user_id` = 转发人，`parent_share_id` = 原帖，`content` = 可空附言）。于是信息流按 `created_at`
  倒序天然把转发行排在最前，详情页按 `user_id` 渲染天然显示转发人。
  **商品快照沿用原帖**（不重新查商品域：转发引用的是原帖内容，重查会让同一内容两处快照不一致）。
  三条拒绝规则：原帖不存在 → 404；转发自己 → 422；同一原帖重复转发 → 409
  （唯一键 `uk_share_user_parent (user_id, parent_share_id)` 兜住并发窗口；
  MySQL 唯一索引把 NULL 视为互不相等，故原创行不受约束）。原帖昵称/内容按
  `loadContext` 一次批量取（一页 10 条转发 = 1 次原帖查询 + 1 次昵称查询，无 N+1）。
  增量 `docs/sql/incremental/14-share-repost.sql`。

> 新增「64 位 id 需要出到前端」的接口时照此办理；**别在前端用 `Number(id)` 转换**。

**权重表（`support/CreditModel`，单一事实来源；全部可由环境变量覆盖，启动即校验和为 100，否则 fail-fast）**：

| 因子 `code` | 满分 `weight` | 计算口径 |
|---|---|---|
| `BASE` 基础分 | 60 | 固定底分（注册即享有） |
| `COMPLETION` 履约完成率 | 18 | `round(18 × 已完成 / 已了结)`，已了结 = 完成 + 关闭 + 退款（不含待付款 / 在途） |
| `REVIEW` 评价质量 | 16 | `round(16 × 平均分 / 5)`，无评价记 0 分 |
| `AFTERSALE` 售后诚信 | 6 | `round(6 × (1 − 被裁定退款数 / 总订单数))` |
| **合计** | **100** | —— |

**等级**（服务端给文案，前端不再维护映射）：`≥90 优秀 / ≥80 良好 / ≥70 一般 / <70 待提升`。

**信用分业务规则（实现约束，改前先读 `CreditService` / `CreditModel`）**：
① **因子和 == 总分**，结构上不可能对不上；② **无数据 = 基础分**（分母为 0 记 0 分，故无交易用户得 60，**不返回 null / 0**）；
③ **单调可解释**（各因子是输入的单调不减函数，v1 不设负分项）；④ 输出按 `[0,100]` 夹取（配置越界的兜底），实际落在 `[60,100]`；
⑤ **交易域不可用返回 `DEGRADED` 503**，而不是按「0 单」计算（「拿不到」≠「真的 0 单」）；
⑥ 售后诚信**只计 `arbitrate_result='APPROVE_REFUND'`**，卖家主动同意退款不算污点；⑦ 回写**同值不写库**（幂等）；
⑧ 内部接口**没有「直接设分」入口**，分数只能由权重算出。

> ⚠️ **`ProductCard.sellerId` 是显式公开例外**：商品 / 闲置详情页要展示卖家信用，卡片因此透出 `sellerId`
> （与公开 `ListingCard.sellerId` 一致）。这是「公开购物决策信息」，不构成内部标识泄露 —— 除它之外，
> 卖家 / 用户的内部标识仍须走内部路由（见 `03` 篇 INV 与 T-25）。

**状态机（`support/CouponStatus`，单一事实来源）**：

任意非终态 ──过期──▶ EXPIRED（终态）

**优惠券业务规则（实现约束，改前先读 `CouponService` / `CouponCodeGenerator`）**：
① **领券幂等靠唯一索引 `uk_coupon_user_tpl(user_id, template_id)`**（一人一模板一张），撞键返回 `replay=true`（**不是 409**）；
② **锁 / 解 / 核销全部 CAS 条件更新**（判断写进 SQL 的 `WHERE`），**不用分布式锁**（INV-1 / INV-2）；
③ **券码 = 随机串 `CP` + 14 位去混淆字符**（字符表去 `0/O/1/I`），**刻意不用雪花主键**（规避 JS 精度坑，INV-16）；
④ **营销域只算「能抵多少」，折扣金额由交易域写入 `t_order.discount_amount`**（营销域**不依赖 openfeign**、不反向调交易域）；
⑤ **`claimable` / `claimableReason` 由服务端算**（涉及领取窗口、库存、该用户已领记录，前端拿不到这些数据）；**未登录访客一律 `claimable=false`**，原因文案「登录后可领取」；
⑥ `COUPON_LOCK_TTL_MINUTES`（默认 **35**）**必须略大于**交易域订单超时关单 30，否则会出现「订单还活着、券已被别人领走」；
⑦ **`USED` 是终态**：核销后不可解锁（v1 明确**券不随退款退回**，退款退的是订单实付金额）；
⑧ v1 **只实现满减**（`FULL_REDUCE`）；一张券只作用于**拆单后商品总额最大的那一单**。

**交易域接入时序**（`duoduo-trade`，直连 8085 调内部接口）：
`placeOrder` 先调 `lock`（失败**抛 422 带人话原因**，如「满 200 元可用」）→ `paySuccess` 调 `consume`（**核销失败则整笔支付不成立**）→ `cancel` / `forceClose` / 超时关单**三处**调 `release`（统一带 `scene` 便于排障）。

## 7.1 AI 导购域 `duoduo-ai:8086`（A9「多多」）

**无状态服务**：v1 刻意不依赖数据库、不落对话历史，上下文由前端回传最近 6 条。

| 方法 | 路径 | 认证 | 请求 → 响应 |
|---|---|---|---|
| POST | `/api/duoduo/chat` | **免**（白名单） | `ChatRequest{message(≤500), history:ChatTurn[](≤6)}` → `ChatResponse{reply, recommendations[], mode}` |
| GET | `/api/duoduo/capabilities` | **免**（白名单） | → `CapabilityView{chatAvailable, mode, hint}`；`mode` = `mock` / `llm` / `unconfigured` |

**契约要点（改前必读）**：
1. **`recommendations` 每一条都来自真实商品库** —— 服务先经商品域 `/api/products/internal/candidates` 召回，再把候选喂给模型，系统提示里硬约束「只能推荐候选列表中的商品」。**结构上杜绝编造**，而不是事后用正则抓幻觉。
2. **`history` 是带角色的轮次**（`ChatTurn{role, content}`），**不是**纯字符串数组：服务端据此区分谁说过什么，`role` 由服务端规范化（只认 `user`，其余一律 `assistant`）—— 直接把它拼进提示词等于把提示词结构的控制权交给调用方。
3. **未登录可问答**：对话本身不承载身份；需要「加购 / 下单」时由回复文案引导登录，页面再补一条登录入口。
4. **限流**：每 IP 每分钟（内存固定窗口），超限 **429 `RATE_LIMITED`**，客户端**不应自动重试**（重试只会更早撞上限）。
5. **三形态降级**：`mock`（`DUODUO_AI_MOCK_ENABLED=true`，回复由**真实候选**拼出）/ `llm`（配 `DASHSCOPE_API_KEY`）/ `unconfigured`（**503 `DEGRADED`**，且 `capabilities.chatAvailable=false`）；LLM 超时同样 503。**mock 与真实模式共用同一条召回链路**，因此冒烟在 mock 下验证的「推荐必须真实」对真实模式同样成立。

## 8. 前端 ↔ 后端映射要点（`frontend/src/api/`）
| 前端 | 后端 |
|---|---|
| `client.ts` 解包 `data`，并保留 `requestId` 供报错定位 | 所有接口统一包络 |
| 401 → 单飞刷新令牌并重放请求（`/api/auth/refresh`） | 令牌在 httpOnly Cookie |
| 5xx/网络错误退避重试 ≤3 次；4xx 不重试 | 错误码表见 §1.3 |
| 分页组件直接消费 `page/pageSize/pageCount/total` | `PageResult` |
| **雪花 ID 一律按业务键使用**（订单号/SPU 号），确需主键时从原始响应文本正则提取 | ID 为 19 位 bigint，JS `JSON.parse` 会丢精度 |
