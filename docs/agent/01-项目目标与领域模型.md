# 01 · 项目目标与领域模型

> 读本文件的目的：让 AI 理解「业务在做什么」，从而在实现细节上有正确判断（而不是机械照搬字段）。
> 所有业务规则的理由都写在源码注释里，这里给的是**全局图景 + 术语表 + 主流程图**。

## 1. 项目目标

**多多宠物商店** = 宠物用品电商 + 宠物闲置二手交易（C2C）的**双边平台**。

| 目标 | 具体体现 |
|---|---|
| 让养宠人买到合适的商品 | 按**物种 / 生命阶段 / 过敏原**筛选与提示（宠物档案与商品适用性比对） |
| 让用户之间能买卖闲置 | 闲置（listing）独立于商品（SPU/SKU）：需审核、可沟通、无库存概念 |
| 让钱**安全**地在买卖双方之间流动 | 平台**资金托管**：买家付款进平台 → 确认收货才放款给卖家 → 退款退回买家；平台按基点抽佣 |
| 让平台可运营 | 类目/品牌维护、内容审核、订单干预（仅待付款强关）、资金对账与异常挂账排查 |
| 让口碑可沉淀 | 评价与晒单（按 SPU 聚合评分、支持追评、支持匿名但保留真实主体） |

**明确不在当前范围内**（见 `08` 与 `07`）：真实微信/支付宝收款（用沙箱渠道替代）、微信小程序、AI 导购、
ES 检索、RocketMQ 削峰、Sentinel 限流、物流轨迹、售后仲裁工单、信用分、优惠券营销、地址簿。

## 2. 参与者（Actor）

| 角色 | 权限模型值 | 能做什么 |
|---|---|---|
| 游客 | （无令牌） | 浏览商品/闲置/评价、搜索、看商品评分 |
| 买家 | `USER` | 加购、下单、支付、确认收货、退款申请（经卖家）、评价、发闲置 |
| 卖家 | `SELLER` | `USER` 全部 + 商家端：看自己的订单、发货、售后退款、结算对账、商品管理 |
| 运营 | `OPERATOR` | 平台后台：报表、资金对账、类目品牌、内容审核、订单干预（强关待付款单） |
| 管理员 | `ADMIN` | 同运营（`OperatorGuard` 判定 `OPERATOR` 或 `ADMIN`） |

> 角色升级路径：注册 = `USER` → 实名（`POST /api/users/me/realname`）→ 申请卖家（`POST /api/users/me/merchant`，**需已实名**）
> → 角色写库为 `SELLER`。**角色是 token 快照，升级后必须重新登录**。
> 运营角色当前**无接口可开通**，需直接改 `t_user.role`（已记为待办 A7/P2）。

## 3. 领域对象与关系

```
User ──1:N── PetProfile                     宠物档案（物种/生日→生命阶段/过敏原）
User ──1:N── CartItem ──N:1── Sku
User ──1:N── Order ──1:N── OrderItem        订单是「多卖家拆单」的结果：一单只属于一个卖家
Order ──1:1── Settlement                    资金托管台账（CUSTODY→RELEASED/REFUNDED）
Order ──1:1── Payment                       支付单（PENDING→SUCCESS/EXPIRED/CLOSED）
Order ──1:N── OrderStatusLog                状态迁移留痕（谁改的、为什么）
Order ──1:N── StockFreeze                   SKU 冻结台账（FROZEN→RELEASED/DEDUCTED）
Order ──1:N── Review                        评价（唯一索引 order_id+user_id+spu_id）
Category ──1:N── Spu ──1:N── Sku            商品主数据，SKU 承载价格与库存
Listing ──N:1── User(卖家)                   闲置：审核通过且在售才对游客可见
```

**关键设计取舍（理解这些才能不写错）**：

| 取舍 | 理由（一句话） |
|---|---|
| 下单**按下单时刻快照**存明细（标题/图/价格） | 商品后续改名改价不得影响历史订单 |
| 一单只属于一个卖家（按卖家拆单） | 发货与结算的主体是卖家，合单会让发货与放款无法归属 |
| 库存扣减不在下单事务内（跨服务） | 用「冻结台账 + 原子条件更新 + 补偿调度」替代分布式事务 |
| 评价按 **SPU × 订单** 唯一，而非一单一评 | 一单常含多件商品，混在一段文字里会让商品维度评分失真 |
| 评价**匿名只脱敏**，真实 `user_id` 保留 | 信用分与风控必须能追溯到真实主体 |

## 4. 核心流程（AI 必须能背下来的主干）

### 4.1 下单到放款（担保交易主链路）
```
加购(校验可售) → 下单[幂等键+唯一索引] → 冻结库存(原子条件更新)
  → 支付预下单(渠道抽象；沙箱返回二维码内容)
  → 回调/扫码确认[验签+金额核对+CAS幂等] → 订单 PAID → 资金进 CUSTODY
  → 卖家发货(SHIPPED，资金仍托管)
  → 买家确认收货 / 发货满 N 天自动确认 → COMPLETED → 放款 RELEASED(扣平台佣金)
  → 冻结转实扣(DEDUCTED)
分支：取消/超时 → CLOSED(释放冻结 + 作废未支付支付单)
分支：退款 → REFUNDED(钱回买家 + 退货入库补偿 RESTOCK_PENDING→RESTOCKED)
```

### 4.2 评价链路
```
评价资格 = 登录态(userId) == 订单事实.userId 且 订单事实.status == COMPLETED
  → 校验 spuId 在该订单明细内 → 唯一索引防重（撞键 → 409）
  → 落库(快照商品标题/图) → 公开列表按 SPU 分页 + SQL 聚合评分
  → 追评一次(受窗口限制，服务端下发 appendable)
```

### 4.3 闲置（C2C）链路
```
用户发布闲置 → PENDING（审核未过）→ 运营审核 APPROVE/REJECT（驳回必填原因，留痕）
  → 游客可见条件：status=ON_SALE 且 audit_status=APPROVED
```

## 5. 术语表（中英/表名/枚举对照，避免歧义）

| 术语 | 含义 | 落地位置 |
|---|---|---|
| SPU / SKU | 商品单元 / 规格单元 | `t_spu` / `t_sku` |
| 闲置 | 用户二手商品（无库存，一件） | `t_listing` |
| 冻结 | 下单占用库存，未实扣 | `t_stock_freeze`、`t_sku.frozen_stock` |
| 可售余量 | `stock - frozen_stock` | 商品域统一口径 |
| 托管 | 买家已付、暂存平台的钱 | `t_settlement.status=CUSTODY` |
| 放款 | 完单后打给卖家（扣佣金） | `RELEASED` |
| 佣金 | `PLATFORM_FEE_BPS`(基点，100=1%) 计算的平台抽成 | 结算时固定，事后调费率不影响历史单 |
| 拆单 | 一次结算按卖家拆成多笔订单 | `POST /api/orders` 返回 `orders[]` |
| 幂等键 | 客户端生成的请求唯一键 | `idempotentKey`；唯一索引兜底 |
| 强制关单 | 运营关闭**待付款**订单 | 仅 `PENDING_PAYMENT` 可操作，422 拒绝其它状态 |
| 追加评价（追评） | 对已发评价补一段 | 每条一次，默认 30 天窗口 |
