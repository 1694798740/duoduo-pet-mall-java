# 00 · AGENT 接管指令

> 你是接手本仓库的 AI 编码代理。本文件规定**你必须怎么做**（机器可执行的指令与门禁）；
> 业务背景见 `01`，代码地图见 `02`，架构不变式见 `03`，待办见 `07`。

## 1. 你的任务定义

**目标**：在 `duoduo-pet-mall-java`（Java 微服务 + React 前端）上，按 `docs/PLAN.md` 的排期与 `07-待办事项与验收标准.md`
的验收标准，**独立完成后续开发**，每轮产出：可编译的代码 + 全绿的自测 + 同步的文档 + 一次 Git 提交。

**你不被允许**：
- 改动既有冒烟脚本的断言使其"通过"（只有一种例外：断言本身写错了，且必须在变更记录里写明原因与旧/新口径）；
- 删除或重命名既有对外接口路径（要演进就加新路径或加可选字段，旧路径标注 deprecated）；
- 跳过 `.workbuddy/` 目录（项目数据，含记忆、工具脚本）；
- 把真实密钥、口令、令牌写入任何文件或提交。

## 2. 每轮任务的标准循环（Workflow Loop）

```
[1] 读 07 待办 → 选定一项 TODO（优先 P0）
[2] 读 03 不变式 + 04 契约中相关部分
[3] 若涉及接口：先更新契约（04 + README §三）再写代码
[4] 实现：mapper → entity（若需新表）→ service（业务规则）→ controller（薄）
[5] 编译：package（命令见 AGENTS.md）
[6] 重建受影响容器 → 等 healthy
[7] 写/跑冒烟：新功能必须新增断言（见 06）
[8] 前端：tsc + build（+ UI 自测）
[9] 文档：PLAN.md 变更记录 + README + 云端台账 + 事项表
[10] 提交推送（同一次提交含 README）
```

**任一阶段失败不要跳过**：`[5]`/`[7]` 失败必须定位到根因（区分「实现错」与「断言错」），
并在变更记录里写明症状、根因、修法 —— 这是本项目的历史惯例，也是后续 agent 的唯一线索来源。

## 3. 硬性技术约束（逐条可验证）

| # | 约束 | 验证方式 |
|---|---|---|
| C1 | 控制器不含业务逻辑（只有参数绑定 + 调 service + 包响应） | 读 Controller 类，方法体应 ≤5 行 |
| C2 | Service 不依赖 `HttpServletRequest`；身份从 `UserContext` 取 | grep `HttpServletRequest` 于 service 目录应为 0 命中 |
| C3 | 所有 SQL 参数化（MyBatis-Plus Wrapper 或 `#{}`） | grep 拼接字符串（`${`）应为 0 命中 |
| C4 | 幂等由唯一索引兜底 | 新增写接口必须说明「幂等键是什么、唯一索引在哪」 |
| C5 | 金额 `long`（分）、时间 `LocalDateTime` 存 UTC、对外时间用 ISO-8601 字符串 | 新增字段时检查类型 |
| C6 | 主键雪花 ID，`id-type: input` 模块 insert 前显式 `setId(idGenerator.nextId())` | 新表 insert 必须能通过冒烟（否则会 `Column 'id' cannot be null`） |
| C7 | 跨域只读走内部接口 + `X-Internal-Token`，且**裁剪字段** | 新增内部接口要写明「返回哪些字段、为什么不返回其它」 |
| C8 | 错误码只用 `ErrorCode` 既有枚举；新增错误码要同步 04 篇与 README | grep 硬编码字符串错误码应为 0 |
| C9 | 日志为结构化 JSON 且带 `requestId`；不记录口令/令牌/隐私 | 新增日志不得包含 `password`/`token`/`receiverPhone` |
| C10 | 前端不把令牌放 URL 或 localStorage（本项目令牌在 httpOnly Cookie） | grep `localStorage.*token` 应为 0 |

## 4. 完成定义（DoD，缺一不可）

一个任务算「完成」当且仅当：

- [ ] 代码编译通过，受影响容器 healthy；
- [ ] 该功能的**端到端断言**已加入对应冒烟脚本，且全绿（给出「跑了几套、各多少项、结果」）；
- [ ] 反向场景也被断言（权限不足、状态不允许、参数越界、幂等重复——至少覆盖与本功能相关的项）；
- [ ] 夹具**自建自毁**（不污染种子数据；改库必复原并自证）；
- [ ] 前端相关：`tsc` 0 错误 + `vite build` 通过（UI 改动再加浏览器自测）；
- [ ] `docs/PLAN.md` 变更记录写明：改了什么、自测暴露了什么缺陷、怎么修的；
- [ ] `README.md` 的接口清单/数字已同步，且与代码在**同一次提交**；
- [ ] 云端台账已同步、事项表状态已更新。

## 5. 遇到未知时的处理顺序

1. **先查仓库**：`docs/PLAN.md` 问题区（I-xx 逐条历史坑）→ `docs/agent/08` → 对应模块源码注释（本项目注释密度高，业务规则的理由都写在注释里）。
2. **再查契约**：`docs/agent/04` 与 `README.md §三`，字段名以 Java DTO 源文件为最终事实（路径在 04 篇每张表上方标注）。
3. **仍不确定**：按「与既有同类实现一致」的原则做最小假设，**在变更记录里显式标注假设**，不要停下来等确认（本项目偏好「先按合理默认推进，事后可追」）。
4. **绝不**：猜测字段名后直接写代码（会静默 400）、跳过冒烟直接提交、为了让测试过而放宽断言。

## 6. 沟通与产出格式（对本项目用户的既有偏好）

- 结论先行；重证据（给出命令、输出、文件路径）；不确定就明说。
- 交付总结需含：**改了什么文件 / 怎么验证的 / 结果数字 / 遗留与下一步**。
- 不要寒暄与填充语；不要重复用户已知的信息。
