# 07 · 待办事项与验收标准（AI 的排期表）

> 用法：按优先级取任务；每项的「验收标准」是**可执行的断言清单**，做完必须逐条成立。
> 优先级定义：**P0** 不做会出错账/数据错；**P1** 明显提升产品完整性；**P2** 工程化与体验；**P3** 后期能力。

## A1 · 历史订单托管单回补（I-14）｜P0 ✅ 完成于 2026-09-18（第八轮）

> **已交付**：`POST /api/admin/settlements/backfill?dryRun=`（运营、幂等）+ `scripts/backfill-smoke.ps1`（88 项断言）。
> 实测：开发库 3 笔 `COMPLETED` 挂账 → 回补后 `abnormal` 返回空。
> **两处与下表的偏差（以实现为准）**：① 参数走**查询串**而非请求体（`@RequestBody` 在「无请求体 + 默认
> Content-Type」下会 415，运营用 curl 调运维接口必踩）；② 佣金口径已由用户确认按**当前 `PLATFORM_FEE_BPS`**
> 重算并随结果留痕（`commissionBps` / `commissionNote`），因为历史费率不可还原。
> 另：`abnormal` 不含 `REFUNDED`，所以「③ 返回空」不能证明退款单补对了 —— 冒烟里另加了逐单断言。

| 项 | 内容 |
|---|---|
| 目标 | M5-8 担保交易上线前的订单没有 `t_settlement` 记录，这些单确认收货时「放款」找不到托管单（只记 ERROR）。写一次性回补脚本按订单状态推断资金状态 |
| 涉及文件 | 新增 `duoduo-trade/src/main/java/com/duoduo/trade/service/SettlementBackfillService.java`、`controller/AdminSettlementController` 加内部入口、`docs/sql/` 加回补说明；新增 `scripts/backfill-smoke.ps1` |
| 草案 | `POST /api/admin/settlements/backfill`（运营，幂等）：扫描 `t_order` 中 `status IN (PAID, SHIPPED, COMPLETED)` 且无结算单的订单，按状态推断：`PAID/SHIPPED → CUSTODY`、`COMPLETED → RELEASED`（金额取 `pay_amount`，佣金按当时 `PLATFORM_FEE_BPS`），`REFUNDED → REFUNDED` |
| 验收标准 | ① 构造 3 笔缺托管单的订单（PAID / COMPLETED / REFUNDED），跑回补后 `GET /api/admin/settlements/summary` 三类金额与笔数**精确增加对应值**；② 重复执行**不产生重复单**（幂等）；③ `GET /api/admin/settlements/abnormal` 回补后**返回空**；④ 已存在托管单的订单**不被改动**；⑤ 冒烟脚本断言以上 4 条并在结尾复原夹具 |
| 风险 | 金额推断错误会永久写错账 → 必须「先 dry-run 输出计划、再执行」；建议接口支持 `dryRun=true` 返回将创建的清单 |

> **已交付**：`t_logistics_track`（幂等唯一键 `uk_track_order_node_time` + 覆盖索引 `(order_no, occurred_at)`）
> + 2 个端点（`/api/logistics/internal/{orderNo}/tracks` 摄入 / `/api/logistics/orders/{orderNo}/tracks` 查询）
> + 交易域发货后补推「已揽收」（`@TransactionalEventListener(AFTER_COMMIT)`，best-effort 不阻断发货）
> + 买卖双方订单详情时间线 + `scripts/logistics-smoke.ps1`（**79 项断言**，含★断言总数守卫）
> + `scripts/e2e/logistics-ui-check.mjs`（真实 Chromium **44 项**）。**A2 至此无遗留。**
> **三处与下表草案的偏差（以实现为准）**：
> ① **路径调整**为 `/api/logistics/internal/…` + `/api/logistics/orders/…`（让同域两端点共用 `/api/logistics` 前缀，
>    网关路由与白名单判定更清晰），非草案的 `/api/internal/logistics/…` + `/api/orders/…`；
> ② **查询放宽到「买家本人 / 该单卖家 / 运营」三类**（草案只写当事人），运营需能查全平台轨迹；
> ③ 无轨迹**回空列表而非 404** —— 「还没物流信息」是正常状态，不是错误。
> **顺带收口**：履约域新增 `OrderFacts` 统一取数口（评价域与售后域各自那份「取订单事实」已漂移，一处 422、一处 503）。

| 项 | 内容 |
|---|---|
| 目标 | 发货后能记录/查询物流轨迹节点，买家与卖家详情页可见 |
| 涉及文件 | `t_logistics_track(order_id, order_no, node_code, node_text, occurred_at, raw)`；`duoduo-fulfilment` 加 `controller/LogisticsController`、`service/LogisticsService`；trade 发货成功后**内部调用**履约域写入首个节点；前端 `OrderDetail` 增加轨迹时间线 |
| 接口草案 | `POST /api/internal/logistics/{orderNo}/tracks`（内部凭据，批量节点，幂等键 `order_no+node_code+occurred_at`）；`GET /api/orders/{orderNo}/tracks`（登录，仅当事人：买家本人或该单卖家） |
| 验收标准 | ① 发货后能查到 1 条「已揽收」；② 追加 3 条节点后按时间正序返回；③ 重复上报同一节点**不产生重复行**（唯一索引）；④ 非当事人查他人订单轨迹 **403**；⑤ 未登录 **401**；⑥ 轨迹接口不返回收货人敏感字段（INV-9） |
| 依赖 | 真实快递公司 API（当前用模拟节点，形态与真实一致） |

## A3 · 售后仲裁工单（`duoduo-fulfilment`）｜P1 ✅ 完成于 2026-09-18（第九轮后端 + 第十轮三端页面）

> **已交付（后端 · 第九轮）**：`t_after_sale` + 8 个端点（`/api/aftersales/**` 6 个 + `/api/admin/aftersales/**` 2 个）
> + `scripts/aftersale-smoke.ps1`（**101 项断言**，逐条覆盖下列六条验收标准 + B-01 边界）。
> **已交付（三端页面 · 第十轮）**：买家 `/after-sales`（我的 / 申请 / 详情 + 申请平台仲裁）、
> 卖家 `/seller/after-sales`、运营 `/admin/after-sales`
> + `scripts/e2e/aftersale-ui-check.mjs`（真实 Chromium **44 项断言**，走完买家→卖家→运营整条链
> 并回接口层确认订单与托管同步 `REFUNDED`、退款金额等于实付）。**A3 至此无遗留。**
> **契约修正**：售后单 `id` 对外改为**字符串**（18 位雪花超过 `Number.MAX_SAFE_INTEGER`，`JSON.parse` 会静默改写）。
> **两处与下表草案的偏差（以实现为准）**：
> ① **补了 `POST /api/aftersales/{id}/escalate`**（买家申请平台仲裁）——
>    草案只有「卖家处理」与「运营裁定」，没写「卖家拒绝后买家怎么办」，缺了它流程就断了；
> ② 「缺裁定说明」判 **422**（走服务层 `businessRule`），不用 `@NotBlank` 判 400 ——
>    这是**流程要求**不是字段格式错；立案的 `reason` 才走注解判 400。
> 另：`APPROVE_REFUND` **会真的执行退款**（复用交易域既有运营侧退款入口），
> 因此「已完成订单（钱已放款给卖家）」的裁定退款会被交易域拒 **422** 并提示走追偿 —— 那是 B-01，不是缺陷。

| 项 | 内容 |
|---|---|
| 目标 | 退款争议可立案、留证、运营仲裁（当前退款只有「卖家一键退」） |
| 涉及文件 | `t_after_sale(order_id, order_no, buyer_id, seller_id, type, reason, images, status, arbitration_result…)`；`duoduo-fulfilment` 加 controller/service；trade 提供「按裁定结果强制退款」的内部入口（复用 `internalOrderFact` 模式） |
| 接口草案 | `POST /api/aftersales`（买家发起，需订单已完成/已发货）；`GET /api/aftersales/mine`、`/seller`；`POST /api/aftersales/{id}/reply`（卖家）；`POST /api/admin/aftersales/{id}/arbitrate`（运营，`APPROVE_REFUND`/`REJECT`，**必须填裁定说明**） |
| 验收标准 | ① 非订单当事人发起 **403**；② 未完成/未发货订单发起 **422**；③ 重复对同一订单同一类型立案 **409**；④ 裁定退款后 trade 侧订单变 `REFUNDED` 且托管转 `REFUNDED`；⑤ 驳回必须带说明（缺说明 **422**）；⑥ 全流程状态可查、有留痕 |

| 风险 | 涉及资金，必须复用现有「唯一索引 + 补偿」模式，禁止分布式锁；新增 `discount` 已在 `OrderView` 中预留 |

## A9 · AI 导购「多多」｜P3
`duoduo-ai` 服务（网关已有 `/api/duoduo/**` 路由与白名单）。验收：① 对话接口可返回基于**真实商品库**的推荐（不得编造商品）；② 未登录可问答、需登录的操作（加购）走前端引导；③ 限流与超时降级（`DEGRADED` 503）。

## A10 · Elasticsearch 检索 ｜P3
商品/闲置检索迁移到 ES（中文分词）。验收：① 同义词与拼音容错可查；② 索引与库**最终一致**（补偿任务 + 对账接口）；③ 库存/上下架变化在 N 秒内反映；④ 检索不可用时**降级回 MySQL 检索**（不允许页面全挂）。

## A11 · RocketMQ 削峰 + Sentinel 限流 ｜P3
验收：① 下单请求入队后异步落库，峰值 QPS 下无超卖；② 死信队列可查可重放；③ 限流触发返回 `RATE_LIMITED` 429 且有明确提示；④ 削峰不改变**幂等与状态机**语义（回归全绿）。

## A12 · 压测与容量验收 ｜P3
验收：① JMeter 脚本覆盖「下单-支付-确认」主链路；② 给出 P95/P99、错误率、瓶颈定位结论；③ 与 `ARCHITECTURE.md` 容量模型对齐（必要则修正模型）。

## 取任务时的固定顺序建议

```
A1（先把账做对）→ A2/A3/A4（履约域连续做，复用度最高）→ A5（营销，涉及资金链路）
→ A6/A7/A8（工程化与体验补齐）→ A9~A13（需要新中间件/资质的重活，最后做）
```
每完成一项：更新本篇状态（在标题后标注 `✅ 完成于 <提交号>`）+ `docs/PLAN.md` 任务清单 + README。
