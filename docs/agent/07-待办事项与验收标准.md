# 07 · 待办事项与验收标准（AI 的排期表）

> 用法：按优先级取任务；每项的「验收标准」是**可执行的断言清单**，做完必须逐条成立。
> 优先级定义：**P0** 不做会出错账/数据错；**P1** 明显提升产品完整性；**P2** 工程化与体验；**P3** 后期能力。

## A1 · 历史订单托管单回补（I-14）｜P0 ✅ 完成于 2026-09-18（第八轮）

> **已交付**：`POST /api/admin/settlements/backfill?dryRun=`（运营、幂等）+ `scripts/backfill-smoke.ps1`（88 项断言）。

> 另：`abnormal` 不含 `REFUNDED`，所以「③ 返回空」不能证明退款单补对了 —— 冒烟里另加了逐单断言。

## A4 · 信用分（`duoduo-fulfilment`）｜P2 ✅ 完成于 2026-09-20（第十二轮）

> **已交付**：`CreditService` + `CreditModel`（权重模型）+ `CreditController`（公开只读）
> + `CreditInternalController`（内部回写 / 批量刷新）+ `CreditRefreshJob`（定时兜底）
> + `scripts/credit-smoke.ps1`（**82 项断言**，逐条覆盖下表四条验收标准 + 边界）。
> **权重模型（可环境变量覆盖，启动即校验和为 100，否则 fail-fast）**：
> `base 60 + 履约完成率 18 + 评价质量 16 + 售后诚信 6 = 100`。各因子先归一化到 `[0,1]` 再乘权重，
> 总分取整并**钳制在 `0~100`**；无任何数据的用户得**基础分 60**（不返回 null）。
> **四处与下表草案的偏差（以实现为准）**：
> ① **新增批量刷新入口** `POST /api/reviews/internal/credits/refresh`（内部凭据）——
>    草案只写单用户回写，但「定时把全量卖家分数同步回用户库」需要枚举+批量，否则回写无从触发；
> ② **交易域不可用返回 `DEGRADED` 503 而非按 0 单计算** —— 「拿不到订单数」和「真的 0 单」是两回事，
>    前者若当 0 会让人误判为「从不履约」，宁可降级不给出错误分数；
> ③ **售后诚信只计 `arbitrate_result='APPROVE_REFUND'`** —— 卖家主动同意退款不算污点（那是负责任的行为）；
> ④ `ProductCard` **透出 `sellerId`** 为显式公开例外（商品/闲置详情页展示卖家信用所必需，与公开 `ListingCard.sellerId` 一致）。
> **顺带收口**：用户域注册默认分由硬编码 `100` 改为可配置 `duoduo.user.credit-default`（默认 60），
> 避免「库里 100、信用分页 60」的分裂；`docs/sql/01-duoduo-user.sql` 与 `duoduo-user/src/main/resources/db/schema.sql`
> 的 `credit_score` 默认值同步为 `60`。
> **幂等**：回写「同值不写库」，重复调用不产生额外写；明细因子和严格等于总分（断言覆盖）。

> 折扣金额由交易域写入 `t_order.discount_amount`**（营销域为被调用方、**不依赖 openfeign**）。

> 无活动 / 会员 / 积分；一张券只作用于**拆单后商品总额最大的那一单**（见 `PLAN.md` B-11 / B-12）。
