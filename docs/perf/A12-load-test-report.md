# A12 压测报告：下单-支付-发货-确认主链路（sync 与 queued 双通道）

> 日期：2026-09-25 · 工具：Apache JMeter 5.6.3（无头模式，JDK 21）
> 环境：本机 Docker Desktop（13 容器全部 healthy），JMeter 与容器同机共宿主（8C16G，WSL2）
> 脚本：`scripts/perf/order-pay-confirm.jmx`（同步全链路）、`order-queued-enqueue.jmx`（入队）、
> `order-pay-confirm-multisku.jmx`（热点验证）、`summarize_jtl.py`（汇总）
> 结果明细：`logs/perf/step*.jtl`、`qstep*.jtl`、`multisku.jtl` 及同名 `-report/`（HTML 报告，不入库）

## 一、测试设计

- **同步通道**：注册（Once Only，409 属预期）→ 登录 → 加购 → 下单（同步）→ 支付 MOCK → 发货（内部凭据头）→ 确认收货，每线程独立用户（139 + 线程号），每循环产生 1 笔完整订单。
- **队列通道**：注册 → 登录 → 加购 → `POST /api/orders/queued` 入队；订单落库由消费者异步完成，`t_order_place_task` 状态机（PENDING → PLACED/FAILED）在 DB 侧计量排空速率。
- **阶梯**：10 / 25 / 50 / 100 线程 × ramp 30s × 稳态 300s；排队列档同参数。
- **夹具**：SKU 2001 库存放大（原值 272 已记录待复原）；Sentinel 下单限流临时放大 `DUODUO_TRADE_PLACE_QPS=5000`（默认 100，避免限流闸门盖住容量数据，测后复原）。

## 二、同步通道结果（全链路 6 步）

| 档位 | 全链路吞吐 | 下单 QPS | 全链路 Avg | 全链路 P99 | 下单 Avg / P95 / P99 | 错误率 |
|---|---|---|---|---|---|---|
| 10 线程 | 526 req/s | ~105 单/s | 18ms | 41ms | 26 / 37 / 48ms | 0.01% |
| 25 线程 | 567 req/s | ~114 单/s | 42ms | 117ms | 86 / 111 / 128ms | 0.02% |
| 50 线程 | 496 req/s | ~99 单/s | 96ms | 529ms | 220 / 493 / 570ms | 0.02% |
| 100 线程 | 494 req/s | ~99 单/s | 192ms | 1104ms | 459 / 1029 / 1156ms | 0.03% |

**特征**：下单 QPS 恒定 ~100/s，延迟随并发线性恶化；加购/发货/确认全程稳定（10-22ms）不劣化。瓶颈精确锁定在**下单（及其后续支付）的订单落库链路**。

## 三、队列通道结果（入队端点）

| 档位 | 全脚本吞吐 | 入队 QPS | 入队 P99 | 入队错误率 |
|---|---|---|---|---|
| 10 线程 | 887 req/s | ~444 单/s | 20ms | 0% |
| 25 线程 | 1689 req/s | ~845 单/s | 32ms | 0% |
| 50 线程 | 1874 req/s | ~938 单/s | 64ms | 0% |
| 100 线程 | 1977 req/s | ~989 单/s | 128ms | 0% |

- **入队容量 ~1000 单/秒**（继续加线程只增延迟不再增吞吐），延迟平稳无恶化拐点。
- **消费排空速率 ≈ 112 单/秒**（t_order_place_task PLACED 增量法实测：14:03→14:20，25004→139148）。与同步通道平台一致——**队列只转移等待，不提高落库上限**。
- 已知测试伪影（非系统缺陷，报告中如实记录）：
  1. 25 线程以上加购出现 422：同 SKU 加购累加数量（`CartService.MAX_QUANTITY=200`），入队速率 > 消费速率时购物车积压累加撞上限；
  2. 任务 FAILED 原因全部为「购物车中没有已勾选的商品」：消费耗时读购物车，同用户连续高频入队时购物车已被上一任务清空。

## 四、热点行验证实验（25 线程 × 2 分钟）

| 场景 | 全链路吞吐 | 下单 QPS | 下单 Avg / P99 |
|---|---|---|---|
| 单 SKU（2001） | 567 req/s | ~114 单/s | 86 / 128ms |
| 3 SKU 分散（2001/2002/2003） | **790 req/s** | **~159 单/s（+40%）** | **43 / 84ms（-50%）** |

**结论成立**：同 SKU 高频下单在 `t_sku` 库存行上形成热点行排他锁串行化，是下单上限的主要组成部分；分散 SKU 后吞吐 +40%、延迟减半。剩余上限来自本地单实例 MySQL 的写入路径（fsync、单表写）。

## 五、瓶颈定位与容量模型对齐

| 层 | 实测 | 与 ARCHITECTURE.md 9.2 模型对照 |
|---|---|---|
| 网关/读路径（登录、加购、发货、确认） | 稳定 10-22ms，100 线程无劣化 | 读 2000-4000 QPS：本机共宿主环境未测到上限，**不构成瓶颈** ✅ |
| 写路径（同步下单） | **~100 单/秒**，P99 1156ms @100T | 模型写服务 500-800 QPS：口径为"写请求 QPS"；实测瓶颈为**单订单多表写事务 + 热点行锁**，单实例单机 Docker 环境无法达到模型值 ❗ |
| 队列准入（入队） | **~1000 单/秒**，P99 <130ms | A11 削峰设计达成设计目标 ✅ |
| 消费落库 | ~112 单/秒 | 与同步上限一致（同一落库链路）✅ 自洽 |

**差距解释**：容量模型的 500-800 写 QPS 是 8C16G 独立部署、面向"请求"的目标值；本次实测环境为 JMeter 与全部容器共宿主的单机 Docker（WSL2），且每笔订单在 trade/fulfilment/product 三域共 10+ 次 DB 写。两者口径与环境均不同，**不构成对模型的否定，但暴露了下单链路的两个可优化点**（见下）。

## 六、优化建议（优先级排序）

1. **热点行拆分**：将单 SKU 库存拆 N 段子行（或 Redis 预扣 + 异步回写），可立即兑现实验中 +40% 的收益；
2. **下单事务瘦身**：placeOrder 事务内非关键写（如结算预估、日志）移出事务，缩短行锁持有时间；
3. **消费并发提升**：`OrderPlaceConsumer` 消费线程数与 Hikari 池（当前 100）对齐调优，压测排空速率是否随之上探；
4. **生产容量复测**：DB 独立部署 + 应用多实例后按 9.3 验收线（目标 QPS×1.5 持续 30min 错误率<0.1%）复测，本报告数据作为基线对照。

## 七、测试局限

- JMeter 与被测系统共宿主，CPU/IO 互相争抢，绝对值偏保守（相对趋势与瓶颈定位可信）；
- 未覆盖多网关实例、多 trade 实例的水平扩展场景（单实例部署为当前形态）；
- 队列档购物车累加伪影使 25 线程以上档的实际入队成功环比显示值偏低（入队端点本身 0 错误）。
