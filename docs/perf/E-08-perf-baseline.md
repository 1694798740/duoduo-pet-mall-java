# 压测基线报告（I-09 · 2026-10-26）

> 目标：给「本地基线还合不合格」一个**可重复、带阈值**的答案（不是再找一次容量上限 —— 那是 A12 的课题，见
> `docs/perf/A12-load-test-report.md`）。
> 工具：`scripts/perf/perf-baseline.mjs`（零依赖，Node 内置 fetch；本机没有 JMeter/k6 的最小方案）。
> 环境：本机 Docker Desktop，17 容器全部 healthy；压测进程与容器同宿主。

## 一、合格线（以及为什么是这些数字）

| 场景类型 | P95 | P99 | 错误率 | 5xx |
|---|---|---|---|---|
| 读接口（商品列表 / 商品详情 / 我的订单） | ≤ 300ms | ≤ 800ms | ≤ 0.5% | 必须为 0 |
| 写前链路（结算预览：跨 trade + product + marketing 内部调用，不落库） | ≤ 800ms | ≤ 2000ms | ≤ 0.5% | 必须为 0 |

依据：

- A12 实测本地读路径稳定 **10-22ms**、下单 P95 在 100 线程下 **1029ms**；
- 读路径给 300ms 是留 **10 倍余量** —— 不因一次 GC 就红，但能拦住「新增一次跨服务调用把读拖慢一倍」；
- 预览按 A12 下单 P95 的 **1/2** 定为 800ms（预览不写库、不冻结库存，只有查询与试算）；
- **5xx 单列且必须为 0**：系统错误不该混进「错误率 0.5%」被平均掉。

## 二、本轮实测（20 并发 × 每场景 15s，另有 2s 预热不计入）

| 场景 | 类型 | 请求数 | RPS | P50 | P95 | P99 | 错误率 | 5xx | 判定 |
|---|---|---|---|---|---|---|---|---|---|
| 商品列表（公开读） | read | 5007 | 333.8 | 58ms | 73ms | 84ms | 0.00% | 0 | PASS |
| 商品详情（公开读） | read | 4352 | 290.1 | 68ms | 85ms | 93ms | 0.00% | 0 | PASS |
| 我的订单（登录读） | read | 30538 | 2035.9 | 9ms | 16ms | 20ms | 0.00% | 0 | PASS |
| 结算预览（跨域写前链路） | write | 24256 | 1617.1 | 12ms | 19ms | 23ms | 0.00% | 0 | PASS |

结论：**四项全部达标**，没有 5xx，没有超时。

## 三、两个必须写下来的坑（压测最容易得出错误结论的地方）

1. **商品列表 / 详情比其它路径慢一个量级（P95 73-85ms vs 16-19ms），不是退化**：
   这两条走商品服务（含 ES 检索与多表组装），而「我的订单 / 结算预览」在本数据量下是单表索引查询。
   判定要看**趋势**（同一场景历轮对比），不要拿不同场景的绝对值横向比。
2. **★ 登录态会改变商品详情的可见性，压测必须区分「带不带 Cookie」**：
   本轮第一次跑出「商品详情 404 率 52%、100% 失败」，根因不是接口坏了 ——
   脚本对所有场景都带了商家登录 Cookie，而商家令牌里带 `X-Tenant-Id`，商品详情按租户过滤，
   于是「第三方商家身份读平台自营商品」返回 404（租户隔离的预期行为）。
   修正方式：`withAuth` 只对真正需要登录的场景为 true。
   教训：**压测的错误率必须先解释来源**，否则会把一次预期行为当成故障去"修"。

## 四、怎么跑

```powershell
node scripts\perf\perf-baseline.mjs
# 加压：CONCURRENCY=50 DURATION=30000 node scripts\perf\perf-baseline.mjs
```

退出码 0 = 全部达标；1 = 有场景越线（可直接进 CI）。压测账号默认 `13600003333 / duoduo12345`，
可用 `PERF_PHONE` / `PERF_PASSWORD` 覆盖。
