# 多多宠物商店 · Java 微服务架构设计（v1.0）

> 技术底座：**Java 21 + Spring Boot 3.2 + Spring Cloud 2023 + Spring Cloud Alibaba 2023**（v1.0 设计时为 17，实际构建用 21）
> 目标形态：参考 闲鱼 / 淘宝 的 B2C + C2C 双供给电商架构，可水平扩容至百万级在线用户。
> 与旧版关系：旧版（Node/Express + SQLite）仅作原型验证，**本设计为正式交付形态**。

---

## 0. 先对齐两件事（避免又做错）

### 0.1 语言栈已纠正
旧版后端是 Node.js，虽然业务完整（31 张表、88 项端到端测试），但**不符合 PRD 里「后端语言：Java（Spring Boot / Spring Cloud 体系）」的硬性要求**，因此重做。

### 0.2 「100 万人同时使用」的工程真相
这不是一句代码能兑现的指标，必须先拆成可验证的容量口径，否则无法设计也无法验收：

| 口径 | 含义 | 数量级 | 对应峰值 QPS |
|---|---|---|---|
| 注册用户 | 累计账号数 | 100 万 | 与并发无关 |
| DAU | 日活 | 20–30 万 | 8k–15k |
| **同时在线** | 同一时刻保持会话 | **10–30 万** | **2万–6万** |
| 峰值 QPS | 大促瞬时承载 | — | **5万–10万** |

**结论**：所谓「100 万人同时使用」，工程上应落到 **峰值 5 万–10 万 QPS、10 万–30 万同时在线**。
这个量级的能力**不是靠选型获得的，而是靠四件事**：无状态水平扩展、分库分表、多级缓存、消息削峰。
本设计的每一层都按这个口径设计，并在第 9 章给出扩容路径与压测验收标准。

> 参照：淘宝/闲鱼在这个量级上用的是「网关 + 数百至数千个无状态应用实例 + 分库分表 + 多级缓存 + MQ 削峰 + 读写分离」，单实例承载通常压在 500–1500 QPS 以内。本设计遵循同一逻辑。

## 2. 服务拆分（8 个业务服务 + 4 个基础服务）

| # | 服务 | 端口 | 核心职责 | 拆分理由 |
|---|---|---|---|---|
| 1 | `duoduo-gateway` | 8080 | 统一入口、路由、JWT 前置校验、限流、灰度、埋点透传 | 接入层独立扩缩容 |

| 5 | `duoduo-fulfilment` | 8084 | 发货、物流轨迹、售后、纠纷仲裁、评价、信用分 | 流程长，异步化程度高 |
| 6 | `duoduo-marketing` | 8085 | 优惠券、活动、会员等级、积分（**优惠券已落地**：领券中心 / 我的券包 / 内部锁·解·核销 / TTL 补偿调度；活动 / 会员 / 积分未做） | 大促独立扩容，避免拖累交易 |
| 7 | `duoduo-ai` | 8086 | 多多智能体：意图路由、RAG、工具调用、SSE、会话记忆 | 资源画像不同（GPU/长连接） |
| 8 | `duoduo-admin` | 8087 | 运营后台：审核、类目配置、风控、数据看板 | 与 C 端隔离，避免后台拖垮前台 |
| — | `duoduo-common` | — | 通用：错误体系、统一响应、日志、幂等、分布式 ID、缓存、脱敏 | 复用，非独立服务 |
| — | `duoduo-api` | — | Feign 接口契约 + DTO（服务间调用契约） | 契约先行，避免接错 |
| — | `duoduo-job` | 8088 | XXL-Job 执行器：超时关单、T+N 结算、售后超时、库存对账 | 与 Web 服务分离部署 |

**为什么这样拆**（而不是按 PRD 模块 17 个拆）：拆到 8 个，是按**事务边界 + 读写特征 + 扩缩容诉求**切的，
不是按产品模块切的。每个服务都能独立部署、独立扩容、独立降级——这才是「百万并发」的真正前提。

## 4. 数据层设计（百万并发的核心）

### 4.1 分库分表

| 表 | 分片键 | 分片策略 | 理由 |
|---|---|---|---|
| `t_order` / `t_order_item` | `user_id` | 16 库 × 64 表 = 1024 片 | 用户维度查询占 95%，避免跨库 |
| `t_payment` / `t_refund` | `order_id` | 同订单库（绑定表） | 与订单同片，避免跨库事务 |
| `t_cart_item` | `user_id` | 8 库 × 16 表 | 纯用户维度 |
| `t_pet_profile` | `user_id` | 8 库 × 16 表 | 纯用户维度 |
| `t_aftersale` | `buyer_id` | 16 库 × 16 表 | 买家维度为主，卖家维度走 ES 冗余索引 |
| `t_product` / `t_sku` | 不分片 | 单库 + 读写分离 + ES | 商品总量可控（十万级），缓存命中率极高 |
| `t_listing`（闲置） | `seller_id` | 8 库 × 16 表 | 卖家维度管理为主，买家检索走 ES |

**订单编号规则**：`雪花 ID`（全局唯一、趋势递增）作为分片内主键，另生成 `order_no`（业务单号）用于展示与对账。
**跨维度查询**（如运营按订单号查单）通过「基因法 + 订单号反解分片位」定位到具体库表，避免全库扫描。

### 4.2 一致性策略

| 场景 | 方案 |
|---|---|
| 下单扣库存 | Redis 预扣（Lua 原子）+ DB 最终一致，异步对账兜底 |
| 支付回调 | **唯一索引 + 状态机 CAS**，天然幂等（不依赖分布式锁） |
| 下单链路 | Seata AT 模式覆盖「订单 + 库存 + 优惠券」三个库 |
| 跨服务通知 | RocketMQ **事务消息**保证「本地事务 + 消息投递」原子性 |
| 资金结算 | 独立 `t_settlement` 表 + 状态机 + 对账任务，禁止直接改余额 |
| 缓存一致性 | **先更新 DB，再删缓存**（Cache-Aside）+ 延时双删 + Binlog 兜底 |

### 4.3 缓存分层

| 层 | 内容 | TTL | 说明 |
|---|---|---|---|
| L1 本地缓存 | 类目树、品牌、热门商品 | 5 min | Caffeine，抗热点，避免 Redis 被击穿 |
| L2 Redis | 商品详情、Session、库存、限流计数 | 30 min | 集群模式 |
| L3 CDN | 商品图、静态资源 | 7 d | 回源率 < 5% |

**防击穿 / 穿透 / 雪崩**：空值缓存 + 布隆过滤器（防穿透）；热点 key 逻辑过期 + 互斥重建（防击穿）；TTL 加随机抖动（防雪崩）。

## 5. 核心链路（含降级）

### 5.1 下单链路（峰值 5 万 QPS 的写法）

```
用户点击下单
  → 网关：JWT 校验、用户维度限流（Sentinel 热点参数）
  → 交易服务：本地「下单凭证」幂等校验（防重复提交）
  → Redis Lua 原子预扣库存（成功才继续，失败立即返回，不落库）
  → RocketMQ 发送「创建订单」消息（削峰，生产者瞬时承接）
  → 消费端串行落库：Seata AT 事务（订单 + 库存流水 + 优惠券锁定）
  → 返回「排队中」，前端 500ms 轮询结果（避免长事务占线程）
支付：
  → 支付网关回调 → 校验签名 → 唯一索引幂等落库 → 状态机 CAS → 发「支付成功」事件
  → 履约服务消费：生成发货单、通知卖家；营销服务消费：发券、加积分
```

**关键点**：把「瞬时写」转成「队列 + 异步落库」，是抗峰值的第一手段；接口层永远不等待长事务。

### 5.2 读链路（商品详情，峰值 10 万 QPS）

```
CDN → 网关(缓存 60s) → 商品服务 L1 Caffeine → L2 Redis → MySQL 从库
                                           ↑ 回源后异步重建，逻辑过期避免阻塞
```
实测目标：商品详情 **P99 < 50ms，缓存命中率 > 98%**，MySQL 直连流量 < 2%。

### 5.3 降级矩阵（保证核心链路 99.95%）

| 依赖 | 不可用时降级策略 |
|---|---|
| Elasticsearch | 搜索降级为 MySQL 关键词查询（结果变差但不挂） |
| 推荐服务 | 降级为热门榜单（本地缓存） |
| AI 服务（多多） | 降级为 FAQ 兜底话术 + 转人工入口 |
| 优惠券服务 | 下单不校验券，标记「券待补校验」，事后冲正 |
| 物流服务 | 展示「物流信息更新中」，不阻塞确认收货 |
| 评价服务 | 异步写入，不影响主流程 |

## 7. 安全与合规

- 认证：JWT 短时效 access（15 min）+ 服务端 refresh（7 d，Redis 存储，可强制下线）
- 网关前置校验签名，服务间调用使用内部 Token + 服务白名单，禁止直连绕过网关
- 越权防护：所有数据访问带 `user_id` 维度校验，禁止信任前端传入的身份
- 敏感数据：身份证/手机号加密存储（AES-256），日志与响应全程脱敏
- 风控：Sentinel 集群流控 + 设备指纹 + 刷单识别 + 禁售品双向拦截
- 合规：食品资质公示、7 天无理由例外明示、AI 生成内容标识、个人信息可删除

| 阶段 | 内容 | 产出（可运行 / 可验收） |
|---|---|---|
| **P0** | 架构设计 + Maven 多模块骨架 + 公共模块（错误体系/统一响应/日志/幂等/分布式 ID）+ 网关 + 用户服务（注册/登录/JWT/宠物档案） | `mvn clean install` 通过；服务可启动；注册登录链路跑通 |
| **P1** | 商品服务（类目/SPU/SKU/商详/搜索）+ 交易服务（购物车/下单/支付/状态机）+ MySQL + Redis + ShardingSphere | 完整交易闭环可跑通（与旧版 88 项冒烟等价） |
| **P2** | 履约服务（发货/物流/售后/仲裁）+ 评价 + 营销（优惠券）+ XXL-Job 分布式任务 | 售后与结算闭环可跑通（**履约 + 评价 + 优惠券已落地，容器 9 个**；XXL-Job 未接，定时任务暂用 `@Scheduled`） |
| **P3** | AI 服务（多多）+ ES 搜索 + RocketMQ 削峰 + Sentinel 限流 + Seata 分布式事务 | 峰值链路与降级预案可演示 |
| **P4** | 可观测（SkyWalking/Prometheus）+ K8s 部署编排 + JMeter 压测报告 | 达到第 9 章验收标准 |

## 11. 与旧版的关系

| 项 | 旧版（已交付） | 本设计（Java 版） |
|---|---|---|
| 后端 | Node.js + Express + SQLite | Java 21 + Spring Boot 3 + Spring Cloud |
| 架构 | 三层单体 | 8 业务服务 + 4 基础服务（微服务） |
| 数据库 | SQLite（单机） | MySQL 分库分表 + Redis + ES |
| 并发能力 | 单机（百级） | 峰值 5–10 万 QPS（集群） |
| 业务资产 | 31 张表设计、状态机、C2C 担保交易规则、88 项测试用例、前端 17 个页面 | **全部复用** |

旧版的**表结构、订单状态机、资金与售后规则、前端页面与接口契约**可直接迁移，不是推倒重来。
